# iPhone + LTE: приложение не грузится

Расследование 2026-10-07 … 2026-10-09. Разобрано до конца в том смысле, что
причина локализована до клиента; **механизм внутри iOS не установлен** и здесь не
выдумывается.

Этот файл — чтобы следующая сессия не начинала с нуля и не повторяла ошибки
измерения, которые стоили здесь больше всего времени.

---

## 1. Симптомы

На iPhone по LTE приложение открывается через раз или не открывается совсем:

- вкладка пустая, в Safari крутится индикатор загрузки;
- в «Сети» запросы висят **без статуса, без инициатора, без размера и без
  времени** — то есть Safari их даже не отправил;
- изредка «пробивает»: через 20–200 секунд всё приходит разом и приложение
  работает;
- на следующий `F5` — снова пусто;
- отдельно: вход не проходит, `POST /api/login` висит и уходит по таймауту.

**Не ломается:** на WiFi на том же телефоне; на Android по той же LTE; на Mac по
той же LTE через телефон как модем; на любом устройстве в других сетях.

## 2. Как устроен путь

```
телефон → оператор → интернет → релей → роутер (192.168.1.1) → 192.168.1.41 → nginx → Go
```

Ключевое для понимания всего остального: **на WiFi телефон из дома не выходит в
интернет**. Роутер подменяет `chat.frament.netcraze.link` локально на
`198.51.100.37` и отвечает сам (200 за 0.24 с). По LTE имя резолвится публично и
идёт к релею. Это два разных пути, и ломался только второй — поэтому все
проверки на WiFi ничего не показывали.

DDNS здесь ни при чём: WAN-адрес роутера `10.17.73.10` — из приватного
диапазона, то есть CGNAT. Публиковать нечего, любой DDNS-провайдер сделает одно
и то же. Туннель обязателен, но менять DDNS не нужно.

## 3. Что установлено

**Релей пропускает ограниченное число одновременных соединений.** Замерено
заглушкой `scripts/lte-probe/` (`probe.frament.netcraze.link`), логи хоста:

| Залп | Дошло до хоста |
|---|---|
| 2 | оба |
| 3 | все три |
| 4 | только `/burst/0` |
| 6 | только `/burst/0` |
| 10 | только `/burst/0` |

Недошедших нет и в логах nginx — релей их не передал, а не потерял по дороге.

**Но это не жёсткий предел релея.** На Mac по той же LTE-сети через телефон как
модем пришло **25 из 25** запросов залпами по десять. То есть ограничение
проявляется только у одного клиента.

**Сравнение, закрывшее вопрос (2026-10-09):**

| Клиент | Сеть | Результат |
|---|---|---|
| Android | LTE, релей | работает |
| Mac | LTE через телефон как модем, IPv4 | работает |
| iPhone | LTE, релей, преимущественно IPv6 | не работает при параллельных запросах |

Одна сеть, один релей, один сайт. Разница только в клиенте.

**IPv6 при этом жив.** HAR с телефона: восемь успешных ответов, все на
`2a00:ab00:403:34::67`. У Mac через телефон глобального IPv6 нет вовсе — раньше
это путало и несколько раз уводило в ложную гипотезу.

**Одиночные запросы на iPhone проходят всегда.** Прогон из четырёх запросов: все
200, от 324 до 1439 мс. Проблема только в параллельности.

## 4. Что исключено, с доказательствами

| Гипотеза | Чем исключена |
|---|---|
| Боевой сервер | счётчики ядра за 45 часов: `ListenDrops`, `ListenOverflows`, `TCPBacklogDrop`, `TCPReqQFullDrop`, `TCPAbortOnMemory` — **0**; nginx отдаёт бандл за 23 мс (198 912 Б gzip — пересчитано 2026-10-12, bundle рос) |
| Роутер и домашняя сеть | 0% потерь до роутера, RTT 0.3 мс |
| DDNS | WAN `10.17.73.10` — CGNAT, публиковать нечего |
| DNS | 25 мс через публичные резолверы |
| Релей как таковой | 25 из 25 с Mac по той же сети |
| IPv6 | восемь успешных ответов с телефона именно по IPv6 |
| iCloud Private Relay | выключен был всё время (проверено) |
| Android | работает по той же LTE (2026-10-09) |
| Service worker | в 17:36 тот же бандл загрузился целиком вместе с аватарками и `api/feed`; причина оказалась в его prefetch 585 КБ, исправлено |

## 5. Что осталось неизвестным

Поведение iOS при одновременном открытии нескольких соединений к одному адресу
через медленный канал. Воспроизводится устойчиво, объяснения нет. Гипотезы
(радиоуправление, `multipath`, особенность очереди соединений iOS) не проверялись
и в документ не занесены — иначе следующая сессия будет строить на них.

## 6. Что сделано в коде

| Правка | Зачем | Чем измерено |
|---|---|---|
| gzip в nginx | холодная загрузка 1 212 989 → 288 710 Б | `curl`, содержимое ответа |
| фавиконка 1024×1024 → 180×180 | 259 КБ, которые gzip не сжимает | `ls` |
| `Cache-Control: immutable` на `/uploads` | без него каждая аватарка перепроверялась при каждой загрузке | заголовки ответа |
| service worker: оболочка `prefetch`, бандлы и картинки `lazy` | SW тянул 585 КБ при каждом обновлении | собранный `ngsw.json` |
| весь CSS в документ, zone.js в документ, манифест и шрифт — после старта | холодная загрузка 7 → 2 соединения | разметка в собранном `index.html` |
| регистрация SW 30 с → 5 с | при 30 с перезагрузка случалась раньше, и обновление не наступало никогда | HAR со старым `main-JKU7KMLV.js` при проде на `main-2OLX7FD7.js` |
| потолок ожидания 30 → 12 с | худший вход ждал минуту: потолок, потом повтор на полном потолке | новое соединение 693–2905 мс, медиана 1137 |
| повтор для `POST /api/login` и `/api/refresh` | вход — единственный запрос, из-за которого приложением нельзя пользоваться | — |
| защита от двойного тапа входа и регистрации | два POST `/api/login` подряд: первый 200 за 444 мс, второй таймаут | devtools |
| плашка «нет связи» / «сервер отвечает с ошибкой» | раньше жила только в чате; на ленте об ошибке не сообщалось нигде | — |
| журнал push не уходит без сессии | два POST `/api/push/log` на странице входа, оба заведомо 401 | HAR |
| **гейт параллельности, стартующий с одного слота** | предел сети неизвестен, константа — догадка | — |

Гейт — главное. Он ведёт себя как медленный старт TCP: с одного соединения,
после серии успехов открывает ещё одно, а первый запрос, **не дошедший до
сервера**, возвращает всё к единице. Ответ любого кода, включая 401 и 500,
доказывает, что дорога открыта: отказ — это всё же ответ.

На Android и Mac он дорастает до потолка за несколько запросов и незаметен; на
iPhone остаётся на том, что сеть действительно несёт.

## 7. Ловушки измерения, которые здесь стоили времени

Их пять, и все пять повторятся.

**1. HAR от устаревшего бандла выглядит правдоподобно.** Все ответы 200, все пути
существуют, ни одного признака, что что-то не так. HAR ссылался на
`main-JKU7KMLV.js`, когда прод уже отдавал `main-2OLX7FD7.js` — и два дня правок
проверяли не тот код. **Всегда начинай с того, какие имена файлов упоминает HAR, и
сверяй их с продом.**

**2. Одиночный запрос проходит — и это ничего не доказывает.** Пять версий подряд
диагноз уводил в провайдера, DNS и IPv6, потому что все три проверяли ровно тот
случай, который не ломается. **Первым делом нужно было сделать один одиночный
запрос через тот же путь: десять минут, и «путь сломан» отделилось бы от
«запросов слишком много» в первый же день.**

**3. На WiFi телефон не выходит в интернет.** Роутер отвечает на имя сам. Любая
проверка в домашней сети проверяет путь, которого проблема не касается.
**Проверять надо на том имени, которого нет в локальной подмене.**

**4. Инструмент надо открыть самому, до того как отдавать.** Две версии пробы
содержали ошибку и не отработали ни разу; обе проверки легли на того, у кого
приложение уже не работало.

**5. HAR пуст — это результат, а не отсутствие данных.** В прозрачном запросе нет
источника вовсе: Safari его не создаёт. Значит запрос не был отправлен — и это
видно только в связке «нет записи в HAR + нет строки в логе сервера за те же
секунды».

## 8. Инструмент

`scripts/lte-probe/` — статическая заглушка, отдаётся по
`probe.frament.netcraze.link` (в панели релея цель `192.168.1.41:8090`). Отдельный
контейнер, вне `docker-compose.yml`.

```sh
scripts/lte-probe/run.sh start | check | stop
```

Проверяет одиночный запрос, залпы 2/3/4/6/10, объём 200 КБ несжимаемых данных и
апгрейд WebSocket. У каждого запроса потолок 12 с, поэтому страница не зависает и
всегда показывает, кто прошёл. `X-Probe-Request` говорит, какой из параллельных
дошёл: так отличается «релей не передал запрос» от «ответ потерялся назад».

**Имя должно быть новым** — см. §2. Старое не попадёт под локальную подмену и не
проверит ничего.

Логи на хосте: `docker logs lte-probe`, группировать по `User-Agent` — так iPhone
отделяется от Mac и Android.

Состояние на 2026-10-12: контейнер поднят четвёртый день и простаивает, за
последние четверо суток к нему пришло 35 запросов, из них 5 с iPhone. То есть
инструмент жив, но расследование закончено и он ничего не стоит.

## 9. Что делать дальше

1. **Проверить iPhone по LTE с нынешним гейтом.** Это единственный незакрытый
   замер: правки от 2026-10-08 на телефоне ещё не работали.
2. Если не помогло — остаётся **одно соединение** на холодную загрузку, то есть
   встроить и сам бандл в документ. Цена: ~195 КБ gzip на каждое обновление.
   Принимать только при доказанном факте, что дело именно в этом.
3. Долгосрочно: туннель с пределом в три соединения — ограничение самого
   приложения. **WireGuard на роутере** убирает релей с пути целиком и заодно
   закрывает приложение от публичного доступа. Это правильное решение, а не
   обходной путь.

## Как устроен доступ снаружи — и где обрыв

Владелец уточнил: **HTTPS терминирует роутер** (встроенный dynamic DNS от
производителя, Netcraze) и перенаправляет на `http://192.168.1.41:3000`.

Отсюда цепочка для телефона в LTE:

```
chat.frament.netcraze.link
  → DNS: 185.162.93.96 / 87.228.71.67
  → TLS терминирует роутер
  → роутер проксирует на http://192.168.1.41:3000
  → home-lab отдаёт SPA и /api/
```

**Поправка к моему вчерашнему анализу.** Я сравнивал `ipify` и `ifconfig.me` и
принял расхождение за VPN на роутере. Это было неверно: из домашней сети эти
сервисы видят **адрес прокси, через который идёт мой трафик**, а не WAN-адрес
роутера. Из дома внешний адрес так измерить нельзя. Вывод про «два внешних адреса»
не имел значения — снимаю его.

**Что проверено и работает:**
- nginx на home-lab настроен для WebSocket верно: `proxy_set_header Upgrade`,
  `Connection "upgrade"`, `proxy_http_version 1.1` (`frontend/nginx.conf:12-17`).
  Со стороны home-lab WS не ломается.
- A-записи домена отвечают: `GET /api/version` на `185.162.93.96:443` → `1.5.1`,
  на `87.228.71.67:443` → то же. То есть внешний вход работает **прямо сейчас**.
- `GET /api/ws?token=fake` с `Upgrade: websocket` → 401 в формате нашего бэкенда.
  Значит WebSocket-запрос проходит через прокси и не срезается.

**Что не проверено и где, по всей видимости, обрыв.** Владелец зафиксировал на
телефоне в LTE: корень открывается, **`/api/` недоступен**. При этом через
интернет (не из домашней сети) `/api/health` отвечает `{"status":"ok"}` — то есть
внешний путь работает.

Раз корень отдаётся, а `/api/` — нет, и при этом из домашней сети и из внешнего
интернета `/api/` работает, то обрыв **не в nginx и не в Go-сервере**. Остаётся
разница между путями, по которым роутер отдаёт статику и API:

1. **TLS-прокси на роутере.** Если он терминирует TLS и перенаправляет на
   `http://192.168.1.41:3000`, то путь `/api/` проходит через ту же схему — и
   должен работать. Значит смотреть надо на то, как именно настроено правило:
   переадресация по домену целиком или с ограничением по пути.
2. **Кэш или service worker.** Если корень закэширован (PWA, `ngsw-config.json`),
   а `/api/` — нет, то приложение откроется «как будто работает», а запросы
   упадут. Это объясняет наблюдение точнее всего: вкладка выглядит живой, но
   ничего не грузится.
3. **Разное поведение по User-Agent или по мобильному трафику.** Роутер может
   отличать мобильный трафик — тогда корень (из кэша) есть, а `/api/` не проходит.

**Что нужно измерить — одно, и это закроет вопрос.** С телефона в LTE открыть:

```
https://chat.frament.netcraze.link/api/health
```

Должно показать `{"status":"ok"}`. Три исхода:

| Что покажет | Что это значит | Что делать |
|---|---|---|
| `{"status":"ok"}` | сеть в порядке, `/api/` работает | проблема в клиенте (этапы 1–2 плана) |
| Таймаут / нет ответа | обрыв по пути `/api/` | правило переадресации на роутере |
| HTML вместо JSON | прокси отдаёт `index.html` на `/api/` — SPA fallback вместо API | правило переадресации на роутере |

Третий исход особенно вероятен и полностью объясняет «корень открывается, API
нет»: SPA-fallback отдаёт `index.html` на любой путь, и клиент получает HTML там,
где ждал JSON.

**И параллельно — проверить на роутере**, как сформулировано правило
переадресации: переадресация всего домена на `http://192.168.1.41:3000` должна
захватывать и `/api/*`. Если там указан только `/` или только корень, в этом и
причина.

## Причина «не открывается через LTE» в клиенте — механизм найден

Разобрал `connectWebSocket` целиком (`api.service.ts:990-1041`).
`wsConnecting` сбрасывается **только** в трёх местах: исключение конструктора
(1005), `onopen` (1011), `onclose` (1035). `scheduleReconnect` зовётся **только**
из исключения (1006) и `onclose` (1037).

```
new WebSocket(...)     → wsConnecting = true        (1000)
  рукопожатие ЗАВИСЛО   → ни onopen, ни onclose не придут
                          wsConnecting остаётся true навсегда
  строка 991: if (this.wsConnecting) return;  → все будущие попытки отброшены
  scheduleReconnect не звался, таймера нет
  → WebSocket мёртв до перезагрузки страницы
```

На LTE пакеты теряются без RST, рукопожатие просто висит. Это в точности то, что
наблюдалось 2026-10-03: HTTP ожил, WS не переподключился, ноль `WS connect` в
логах за 10 минут.

**Правка (локально, риска для прода нет):**
1. Таймаут на установление соединения, 10–15 с: `close()`, сбросить `wsConnecting`,
   позвать `scheduleReconnect`.
2. `this.ws.onerror = () => {}` (строка 1040) — хотя бы логировать.
3. `WS_SLOW_POLL_DELAY = 60000` (строка 324) не реализован нигде, только
   вычисляется. Либо реализовать, либо удалить, чтобы не вводил в заблуждение.
4. Тест: сокет, не вызывающий ни `open`, ни `close` → через таймаут уходит в
   переподключение.

### Этап 1. WebSocket в клиенте — ✅ сделано локально, ждёт деплоя

Механизм: `wsConnecting` сбрасывается только в исключении конструктора, `onopen` и
`onclose`. На LTE пакеты теряются без RST, рукопожатие висит, ни один из трёх
обработчиков не приходит → `wsConnecting` остаётся `true` навсегда → строка
`if (this.wsConnecting) return;` отбрасывает все будущие попытки → сокет мёртв до
перезагрузки страницы.

Что сделано в `api.service.ts`:

1. **Сторож рукопожатия**, 12 с (`WS_CONNECT_TIMEOUT`). По истечении сокет
   отбрасывается и планируется переподключение.
2. **`#dropSocket()`** отсоединяет обработчики **до** `close()`, иначе `close()`
   вызвал бы `onclose` и запланировал второе переподключение поверх первого.
3. **`onerror`** больше не пустой — пишет в консоль с номером попытки.
4. **Убран мёртвый slow-poll.** `WS_SLOW_POLL_DELAY` вычислялся, но никакого
   опроса по нему не было: после 20 попыток задержка просто прыгала с 30 с на
   60 с. Теперь backoff упирается в потолок 30 с и не растёт дальше — пауза в
   минуту выглядит как мёртвый сокет и ничего не даёт. Поле `WS_MAX_RETRIES`
   удалено: после правки оно ничего не читало.

**Проверка.** 9 новых тестов в `api.service.spec.ts` (272 всего). Мутационные
проверки, каждая ловит:

| мутация | что падает |
|---|---|
| сторож отключён (`if (false)`) | 3 теста |
| `#clearConnectTimer()` убран из `onclose` | «watchdog armed after a clean close» |
| `#clearConnectTimer()` убран из `onopen` / из `catch` | соответствующие тесты |

Тест «не оставлять сторож взведённым» написан отдельной проверкой поля, а не через
поведение: по наблюдаемым эффектам «таймер не чистится» и «сторож ничего не делает»
неразличимы — ровно тот случай, когда тест проходит при живой ошибке. Такую мутацию
первый вариант и пропустил.

### Этап 2. Дубликаты сообщений — ✅ сделано локально, ждёт деплоя

**Причина подтверждена на проде:** дублей в БД **ноль** (224 сообщения), значит
показа трижды — строго клиентское явление. Все 69 WS-подключений в логах — с одним
и тем же токеном: старый сокет не закрывается при обрыве сети, новый открывается
поверх. Сервер честно шлёт кадр на каждое соединение получателя, поэтому три
сокета дают три показа. Клиент обязан дедуплицировать — и не делал.

**Механизм в коде.** Проверка стояла **до** `await` расшифровки, а `push` — **после**:

```ts
if (data.id && this.messages.some(m => m.id === data.id)) return;   // проверка
...
const viaEnv = await this.crypto.decryptViaEnvelope(...);           // await
const decrypted = await this.crypto.decrypt(...);                   // второй await
this.messages.push(msg);                                            // добавление
```

Три кадра одного сообщения проходят проверку до того, как кто-либо добавится.

**Что сделано в `chat.ts`:**

1. **`seenMessageIds`** — `Set<number>` вместо сканирования массива при каждом кадре.
2. **`claimMessage(id)` вызывается после расшифровки, непосредственно перед `push`** —
   окно между проверкой и добавлением закрыто. Обе ветки: личные чаты и группы.
3. **`reindexSeen()`** при переключении чата — индекс следует за списком.
4. **Загруженные с сервера сообщения тоже занимают свои id** — иначе кадр, пришедший
   сразу после загрузки, добавил бы дубль.
5. **`finalizeOptimistic`** переводит временный id на серверный в индексе; без этого

6. **`rollbackOptimistic`** возвращает id в свободное состояние.

**Проверка.** 7 новых тестов в `chat.dedup.spec.ts` (279 всего). Первая версия теста

последний резолвер, первые два промиса не завершались, дубликаты просто не
доходили до `push`, и утверждение было не про то. Переписана: резолверы
накапливаются, тест проверяет, что все три дошли до расшифровки и что все три

### Этап 3. Темп запросов при старте + утечка сокетов — ✅ сделано локально

Разбор HAR дал механизм: шесть запросов к `/api` за одну секунду, и каждый со своим

1. **Регистрация устройства отложена на 2.5 с** (`SETTLE_AFTER_PAINT_MS`). Она нужна

   Backlog.

**Утечка сокетов в бэкенде** — то, что владелец просил не забыть:

1. **`closeConn()` — единая точка закрытия.** Сокет выбрасывался из `h.clients`
   семью разными способами, и все семь мест, где это делалось по ошибке записи,

2. **`MaxConnsPerUser = 2`** и `dropStaleSockets()`: при новом подключении лишние

   поэтому возраст хранится в `connOpened`).
3. **`unregister` больше не уменьшает счётчик безусловно** — только через

   сокет, уже вычищенный потолком, уменьшал счётчик второй раз.
4. **Порядок вычистки исправлен:** сначала вставка, потом обрезка. Обрезка перед
   вставкой оставляла в карте `MaxConnsPerUser + 1` — это поймали тесты.

## Разбор второй проверки с телефона (2026-10-06)

Владелец: перенос строки на iPhone не работает; health обрывается **через 3 секунды**,
остальные `/api` висят дольше; HTML и JS через LTE приходят мгновенно, а на WiFi
мгновенно всё; подозрение — порты, адрес прослушивания Go, нужен nginx.

### «Через 3 секунды» — это наш код, а не сеть

`app.ts:518`: `interval(3000)` + **`switchMap`**. `switchMap` отменяет незавершённый
внутренний запрос, когда приходит следующий тик. То есть каждый опрос health
получал **ровно 3 секунды на ответ** и отменялся, если не успел, — снова и снова,
бесконечно. Это и есть наблюдаемый «обрыв через 3 секунды».

Другие `/api` не отменяются ничем, поэтому «висят гораздо больше» — до таймаута
самого браузера. Наблюдение владельца было точным, объяснение — в нашем коде.

Тогда же нашлись два соседних дефекта в том же месте:

- у подписки **не было `error`-обработчика**: первый же сбой на мобильной сети
  завершал поток, и опрос maintenance умирал до перезагрузки страницы;
- таймаута не было вовсе.

**Правка:**

| | было | стало |
|---|---|---|
| оператор | `switchMap` (отменяет) | `exhaustMap` (пропускает тик, не отменяет) |
| интервал | 3 с | 15 с |
| таймаут | нет | 10 с |
| ошибка | рвёт поток | `catchError` → «нет ответа» |
| «нет ответа» | — | не меняет состояние (иначе перезагрузка посреди maintenance) |

Инвариант: **таймаут обязан быть не больше интервала**, иначе запрос снова окажется
в полёте к моменту следующего тика. Тест это проверяет.

### HTML/JS «мгновенно через LTE» — сравнение некорректно

`ngsw-config.json`, группа `app`: `installMode: "prefetch"`, файлы `/*.js`, `/*.css`,
`/index.html`. **Service worker отдаёт их из кэша, в сеть они не ходят вообще.**
`dataGroups` пуст, поэтому в сеть ходит только `/api`.

Отсюда: «статика быстрая, API медленный» не доказывает ничего про сеть и уж точно
не указывает на второй контейнер. Сравнивать надо было /api по LTE с /api по WiFi.

### Порты, адрес Go, nginx — проверено, не при чём

```
curl напрямую в Go   :8080/api/health → 0.0004 с
через nginx          :3000/api/health → 0.0006 с
статика через nginx  :3000/index.html → 0.0004 с
```

Хоп контейнер→контейнер — **микросекунды**. Go слушает `:8080` (все интерфейсы),
`proxy_pass http://backend:8080` в nginx уже есть, это и есть реверс-прокси.
Менять здесь нечего.

### Открытая гипотеза: AAAA-записи

У домена есть IPv6-адреса:

```
2a03:21c0:0:227::96   Miran Ltd., Санкт-Петербург
2a00:ab00:403:34::67  JSC Selectel, Санкт-Петербург
```

Ни один не ответил на 443 в моих проверках, но **проверить это честно я не могу**:
ни у моей машины, ни у home-lab нет глобального IPv6 (только ULA `fdd0:…`).
Мобильные операторы обычно IPv6-first, поэтому если AAAA указывают на нерабочий
IPv6, телефон сначала идёт туда, ждёт и только потом откатывается на IPv4. Это
хорошо объясняет «на WiFi работает, на LTE нет».

**Как проверить:** с телефона в LTE открыть `https://chat.frament.netcraze.link/api/health`.
Если он открывается, но приложение нет — смотреть AAAA. Быстрый способ обойти —
убрать AAAA-записи у DDNS-провайдера.

## Проверка 2026-10-06, вторая итерация

Владелец: `/api/health` всё ещё открывается как Angular. Плюс наблюдение, что это
не провайдер — с отключённым кэшем HTML и JS по LTE приходят за 5–20 мс.

### Сервер отдаёт JSON, дело в service worker

В логе nginx (тайминги добавлены в этом же заходе):

```
17:58:16  192.168.1.1 "GET /api/health HTTP/1.1" 200 req=0.001 up=0.001 ua="curl/8.7.1"
```

Запрос доходит, ответ 200 за **1 мс**. То есть сервер в порядке, а `index.html`
отдаёт **старый service worker из своего кэша**: он считает навигацией любой путь
без точки. Правка `navigationUrls` уже в образе, но у клиента работает прежний SW,
пока приложение не обновится.

Проверить, не обновляя: **приватная вкладка** (в ней SW не зарегистрирован) или
`fetch('/api/health')` из консоли — это XHR, а не навигация, SW его не подменяет.

### Найдено в логе: WebSocket долбится просроченным токеном

```
17:58:09  GET /api/ws?token=… 401   ua="…iPhone…"
17:58:17  GET /api/ws?token=… 401   тот же токен
17:58:18  GET /api/ws?token=… 401   тот же токен
```

Тот же токен, три раза, и **ни одной строки `/api/refresh`**. Токен истёк в
17:04, запросы идут в 17:58.

Причина: `app.ts:409` на старте звал `connectWebSocket()`, который открывает сокет
с тем, что лежит в `localStorage`, — без проверки срока. Сервер отвечает 401,
рукопожатие не проходит. Путь переподключения срок проверял и обновлял токен;
путь старта — нет.

**Правка:** на старте `retryConnection()` вместо `connectWebSocket()`. Он сначала
проверяет токен и обновляет его. Плюс: при **неудачном** обновлении сокет больше
не открывается — открывать его с заведомо просроченным токеном значит гарантированно
получить 401, и именно это давало серию 401 без единого refresh рядом.

## Итог по LTE: сеть в порядке, дело было в приложении

Проверка владельца: `https://chat.frament.netcraze.link/api/health` **в приватной

| Что | Проявление |
|---|---|
| `ngsw` без `navigationUrls` | `index.html` вместо JSON при заходе на `/api/*` — и невозможно проверить API вручную |

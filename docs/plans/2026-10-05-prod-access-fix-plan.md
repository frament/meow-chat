# План исправлений, 2026-10-05 (прод доступен)

## ⚠️ Найдена уязвимость — она первая в очереди

**JWT_SECRET на проде не задан. Используется дефолт из исходного кода.**

```
docker exec my-chat-backend-1 printenv | grep -c JWT_SECRET   →  0
```

`backend/auth/jwt.go:14-20`: при пустом `JWT_SECRET` подставляется строка
`my-chat-dev-secret-change-in-production`. Она лежит в коде, а репозиторий
**публичный** (`github.com/frament/meow-chat` → 200, `private: false`).

Проверено: токен, подписанный этой строкой, **принимается сервером как админский** —
`GET /api/users` от него вернул 200. Запрос был только на чтение; ничего не изменял.

**Что это значит.** Любой, кто увидит адрес домена (из push-уведомлений, из истории
Safari, из логов на телефоне — `chat.frament.netcraze.link` уже засветился в
`CHANGELOG.md` и в сессионных заметках), может сам подписать себе токен с
`is_admin: true` и получить полный доступ: читать и писать любые сообщения,
создавать группы, раздавать инвайты, отключать пользователей. Угадывать адрес не
нужно — он в публичном репозитории.

Это не теоретическая находка и не «улучшение гигиены». Секрет известен всем.

**Что нужно сделать (в таком порядке):**

1. Сгенерировать новый секрет: `openssl rand -base64 48`.
2. Положить его в `.env` на сервере: `JWT_SECRET=<новое>`.
3. Пересоздать backend: `docker compose up -d --no-deps backend`.
4. **Ожидаемое последствие — все открытые сессии разлогинятся**, потому что
   токены подписаны старым секретом. Это не поломка, это желаемое поведение.
5. Добавить в `docker-compose.yml` обязательное требование: без `JWT_SECRET`
   в окружении бэкенд **не должен стартовать**. Сейчас он молча деградирует к
   дефолту — это и есть корень проблемы. Тест в `backend/auth` на «пустой секрет →
   отказ на старте».

Пункт 5 — главный. Пока код молча соглашается на дефолт, секрет потеряется снова
при следующем пересоздании контейнера.

Отдельно: в `backend/auth/jwt.go:17` дефолт стоит в самом коде. После пункта 5
этот откат можно убрать.

## Как на самом деле устроен доступ снаружи

Проверил по пунктам:

```
домен chat.frament.netcraze.link
  → A-записи: 185.162.93.96 и 87.228.71.67
                (Санкт-Петербург: Miran Ltd, JSC Selectel)
  → домашнего адреса 193.233.203.229 в A-записях НЕТ
  → home-lab не слушает 443 вообще
  → ни cloudflared, ни frpc, ни autossh на сервере нет
```

То есть **трафик извне приходит не на домашний роутер, а на сторонний хостинг в
Санкт-Петербурге**, и тот уже как-то пробрасывает его внутрь. Проброс порта на
роутере в этой схеме не участвует — или участвует, но не как «порт 3000 наружу».

Отсюда важное уточнение для плана: **проверять «проброс 3000 на роутере» смысла
имеет мало**, пока не выяснено, как устроена эта внешняя площадка. Скорее всего,
именно она и обрывает WebSocket.

Проверил WS через домен с поддельным токеном:

```
GET /api/ws?token=fake  (Upgrade: websocket)
→ HTTP/1.1 401 {"error":"Invalid token"}
```

Ответ дошёл до нашего бэкенда (`{"error":"Invalid token"}` — это его формат
ответа), значит прокси **передаёт WebSocket-запрос**. Но это проверка на этапе
HTTP-обмена: успешный `101 Switching Protocols` с боевым токеном не проверен, для
этого нужен валидный токен, а он истёк.

Отдельно: с сервера видны **два разных внешних адреса** (`ipify` → `193.233.203.229`,
`ifconfig.me` → `46.160.138.106`), оба за рубежом. VPN на роутере, по вашему
словам, маршрутизирует наружу только для некоторых адресов — это объясняет
расхождение и **не ломает входящий доступ**.

## Причина «не открывается через LTE» в клиенте — механизм найден

Разобрал `connectWebSocket` целиком (`api.service.ts:990-1041`).
`wsConnecting` сбрасывается **только** в трёх местах: исключение конструктора
(1005), `onopen` (1011), `onclose` (1035). `scheduleReconnect` зовётся **только**
из исключения (1006) и `onclose` (1037).

```
new WebSocket(...)     → wsConnecting = true        (1000)
  рукопожатие ЗАВИСЛО   → ни onopen, ни onclose не придут
                          wsConnecting остаётся true навсегда
  строка 991: if (this.wsConnecting) return;  → все будущие попытки отброшены
  scheduleReconnect не звался, таймера нет
  → WebSocket мёртв до перезагрузки страницы
```

На LTE пакеты теряются без RST, рукопожатие просто висит. Это в точности то, что
наблюдалось 2026-10-03: HTTP ожил, WS не переподключился, ноль `WS connect` в
логах за 10 минут.

**Правка (локально, риска для прода нет):**
1. Таймаут на установление соединения, 10–15 с: `close()`, сбросить `wsConnecting`,
   позвать `scheduleReconnect`.
2. `this.ws.onerror = () => {}` (строка 1040) — хотя бы логировать.
3. `WS_SLOW_POLL_DELAY = 60000` (строка 324) не реализован нигде, только
   вычисляется. Либо реализовать, либо удалить, чтобы не вводил в заблуждение.
4. Тест: сокет, не вызывающий ни `open`, ни `close` → через таймаут уходит в
   переподключение.

## Порядок работ

### Этап 0. Безопасность (сделать до всего остального)

JWT_SECRET, см. первый раздел. Дальше всё остальное можно делать спокойно.

### Этап 1. WebSocket в клиенте

Таймаут рукопожатия, `onerror` в лог, убрать мёртвый slow-poll. Локально, без
риска для прода.

### Этап 2. Дубликаты сообщений

Причина подтверждена: дублей в БД нет, 69 соединений на один токен. Правка в `chat.ts`:

- проверка дубля — **рядом с добавлением, после `await` расшифровки**. Сейчас
  строки 1200 и 1245 проверяют до `await` на 1206/1212, а `push` на 1230 — между
  ними два `await`, за это время проходит любой второй кадр;
- `Set` обработанных id вместо сканирования массива;
- тест «три одинаковых кадра подряд, с `await` между ними → одно сообщение».

Отдельно — утечка сокетов (69 подключений на один токен, 35 из них за полчаса).
Работа в `handlers.go`: сокет закрывается только при явном отключении клиента, но
не при потере сети.

### Этап 3. Понять, где обрывается внешний доступ

Раз выяснилось, что снаружи есть сторонний хостинг, надо понять его роль:

1. Где физически стоит площадка, дающая `185.162.93.96` / `87.228.71.67`, и что
   там настроено (nginx, туннель, прокси).
2. Есть ли там ограничения на WebSocket и на долгоживущие соединения.
3. Проверить с телефона **не из домашней сети**, открывается ли
   `https://chat.frament.netcraze.link` вообще. Для этого curl не нужен —
   достаточно открыть адрес в браузере телефона при выключенном Wi-Fi.

## Ответ на «как сделать curl с телефона»

Не нужно. Открываете в Safari телефона, **выключив Wi-Fi**:

```
https://chat.frament.netcraze.link/api/health
```

Должно показать `{"status":"ok"}`. Если показало — сеть и внешний доступ в порядке,
значит дело в приложении (этапы 1–2). Если не показало — обрыв во внешней
схеме (этап 3). Этот один тест закрывает половину вопросов без единой команды.

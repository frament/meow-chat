# План: как оповещать пользователей об обновлении версии

## 1. Проблема, которую надо решить

Сейчас в приложении есть **только «доступно обновление»** и ничего для «обновление установлено».

`GET /api/check-update` возвращает `{update_available, current_version, latest_version, download_url, release_notes_url}` и кэшируется на час. Фронт рисует баннер «Доступна новая версия 1.5.0» + кнопку «Скачать» (в `app.ts` и в настройках). Дальше:

- заметки о релизе лежат **на GitHub** и открываются ссылкой; у члена семьи без аккаунта на GitHub эта ссылка бесполезна;
- `GitHubRelease` в `handlers/update.go` читает только `tag_name` и `html_url` — тело релиза не запрашивается вообще;
- как только версии совпали, баннер исчезает, и **узнать, что изменилось, нельзя ниоткуда**;
- `CHANGELOG.md` написан по-русски и подробно, но в приложение не попадает.

## 2. Главная техническая сложность: версия сервера ≠ версия интерфейса

`/api/version` отдаёт версию **бэка**. Фронтенд о своей версии не знает вообще — метки `APP_VERSION`/`appVersion` в коде нет.

Из-за service worker это не мелочь: после раскатки у части клиентов ещё неделю живёт старый бандл. Значит, надпись «версия 1.5.0» в UI может быть **ложью** — человек смотрит на 1.4.0 и читает notes к 1.5.0. Это прямо противоположно цели «предупредить о changes перед обновлением».

Отсюда решение: **обе версии нужны и они должны быть видны раздельно.**

| Что | Откуда | Зачем |
|---|---|---|
| Версия бандла | константа в бандле, собирается тем же трюком, что и серверная — из `backend/version/VERSION` на этапе `make build` (через `npm pkg`/define) | «что ты сейчас видишь» |
| Версия сервера | `GET /api/version` | «что обслуживает запросы» |
| Расхождение | сравнение на клиенте | «у тебя отстал интерфейс, обнови PWA» |

Пока расхождения нет — показываем «что нового» и для бандла, и для сервера. Как только появилось — приоритет у интерфейса, потому что его человек видит.

## 3. Кому показывать

Здесь важно не ошибиться: обслуживают сервер **все**, а обновляет его **один человек**.

- **Всем:** тихое, ненавязчивое — «В версии 1.5.0: подтверждение копирования, исправлены иконки». Одна строка, без кнопок и красоты. Человек не должен гадать, что сломалось, когда интерфейс стал выглядеть иначе.
- **Админу:** подробно — полный список изменений, что именно установлено, что доступно к обновлению, инструкция, ссылка на откат. Админ — единственный, кому это actionable.

Никаких модалок на весь экран и никаких push «вы обновились» остальным: обновление сервера их не касается, а всплывашка без причины убирает доверие к следующей.

## 4. Источник текстов

Тексты берём из **того же CHANGELOG.md**, что уже пишется на русском. Не дублируем их в коде — дублирование разъедется, как уже разъехались счётчики тестов и номер версии.

Варианты, от худшего к лучшему:

1. **Релевант с тела GitHub Release.** Ноль работы, но нужен GitHub, а у семейного пользователя его нет, и формат чужеродный (markdown отрендерится, но в чужом оформлении).
2. **Рендер `CHANGELOG.md` на бэкенде при старте.** Файл уже есть в образе (проверить: `backend/.dockerignore` режет `*.md` — понадобится исключение). Сервер сам находит секцию своей версии, отдаёт кусок. **Предпочтительно**: тексты не дублируются, доступно офлайн, язык наш.
3. Отдельный API «релизных заметок» с кэшем. По сути то же, что (2), но лишний слой.

Выбираем (2). Отдавать наружу весь `CHANGELOG.md` целиком нельзя — там внутренние заметки о CI и памяти.

## 5. Соглашения, которые надо зафиксировать заранее

- Секция в `CHANGELOG.md` начинается со строки ровно `## [X.Y.Z]` — это уже так, и это уже проверяет `scripts/check-version.sh`.
- Текст секции — только пользовательские изменения. Внутренние (CI, рефакторинг, разбор инцидентов) либо в `### 🔧 Internal`, либо вообще в документ сессии.
- Первые абзацы читаются как «что изменилось для меня», остальное — по желанию.
- Новую секцию пишем **до** тега, а не после: тег без заметок = релиз без описания.

## 6. Что уже готово и что придётся доделать

Уже есть и работает:

- кэш проверки обновлений на час (`updateCache` в `handlers/update.go`) — для релизных заметок такой же приём, чтобы не дёргать GitHub на каждый вход;
- `release_notes_url` в ответе, который можно переиспользовать;
- `version.Version` теперь единственный источник номера (встраивается в бэка), значит серверная версия всегда правда;
- `scripts/check-version.sh` в CI — наличие секции в CHANGELOG уже проверяется.

Придётся сделать:

- [ ] Отдавать `body` релиза в `GitHubRelease` (или перейти на CHANGELOG — по п. 4).
- [ ] Парсер секции `## [X.Y.Z]` в `CHANGELOG.md` + `GET /api/release-notes`.
- [ ] Версия бандла во фронте (define при сборке), сравнение с серверной, флаг «интерфейс отстал».
- [ ] Компонент «Что нового»: одна строка для всех, развёрнутый список для админа.
- [ ] Показ один раз на версию: `localStorage`-ключ вида `seen-notes:1.5.0`, чтобы не доставать при каждом входе.
- [ ] Проверка, что на сервере `1.4.0` с клиентом `1.5.0` (откат) — приложение не должно ругаться; просто показывать notes сервера, без призывов обновиться.

## 7. Решения, которые нужно принять владельцу

1. **Тексты только из CHANGELOG или ещё и из релизных заметок GitHub?** Я предлагаю только CHANGELOG: он уже есть, на русском, и в нём нет мусора.
2. **Показывать ли «что нового» всем, или только админу?** Я предлагаю всем, но одну строку. Если семья сочтёт лишним — легко сузить до админа одной проверкой прав.
3. **Тексты на языке пользователя или только по-русски?** Сейчас приложение русскоязычное, i18n нет. Оставляем русский; если появится английский — формат секций придётся оговорить отдельно.
4. **Срок жизни подсказки про отставание интерфейса.** Показывать неделю (типичное время жизни PWA-кэша) или пока пользователь сам не обновится?

## 8. Почему это не срочно

Сбой, который приносит реальные потери, — это не «не знаю, что обновилось», а «после обновления сломалось и непонятно, что именно». Поэтому в порядке приоритета (см. «Порядок работы»): сначала `v2.3.0` как **процесс** (checksums, rollback, healthcheck после рестарта, авто-revert), и только потом — подача изменений пользователю. Плашка «что нового» — это последнее, а не первое: она улучшает впечатление, а не надёжность.

Правило простое: **сначала невозможно тихо сломать, потом можно вежливо сообщить об изменениях.**

# Устройства, авторизация и раздача ключей: стратегия

Заведено 2026-10-11 по трём требованиям владельца: устройства не должны дублироваться,
новое устройство должно сообщить о себе **до** открытия интерфейса, авторизованное
устройство должно получать все ключи всех чатов.

Продолжение `docs/plans/e2ee-new-device-key-flow.md`. Тот план разбирал вход нового
браузера; здесь — жизненный цикл устройства целиком. Раздел 6 старого плана местами
устарел, поправки в конце.

---

## 1. Что происходит сейчас (проверено по коду)

### 1.1 Регистрация

`user_devices` (`database.go:432`): `device_id TEXT NOT NULL UNIQUE` — **уникален глобально**,
не в паре с пользователем. Регистрация:

```sql
INSERT INTO user_devices (...) VALUES (...)
ON CONFLICT(device_id) DO UPDATE SET last_seen = ..., device_name = ..., device_public_key = ...
```

`user_id` в `DO UPDATE` **не участвует**.

Отсюда два следствия, и оба воспроизводимы:

- **Общий браузер у двух участников.** Второй логинится, шлёт свой `device_id` — сервер
  обновляет строку, которая принадлежит **первому**. В списке устройств второго её нет, и
  `getUserDeviceKeys(второй)` её не вернёт, то есть ключи этому устройству не доедут никогда.
  При этом в списке **первого** появится чужое устройство с чужим именем.
- **Дубли у одного пользователя.** `deviceId` генерируется заново, когда ключевой материал
  стёрт (восстановление ключей чистит store целиком — `key-recovery.spec.ts:47`), а старая
  строка остаётся навсегда. Удаление есть (`devices.go:113`, корректно ограничено `user_id`),
  но на руках.

Отдельно — дыра в `ensureDeviceKeyPair` (`crypto.service.ts:423`): если `deviceKeyJWK` и
`devicePublicKeySPKI` на месте, а `deviceId` нет, функция выходит по раннему `return`,
оставив `this.deviceId = ''`. Дальше `registerThisDevice()` честно уходит (`if (!this.crypto.deviceId) return`),
и устройство молча не регистрируется.

Выход при входе не трогает IndexedDB — только `localStorage` (`api.service.ts:470`). Поэтому
на одном браузере ключи первого пользователя переживают выход второго.

### 1.2 Вход нового устройства

Механизм **уже есть**, и он правильный: `checkDeviceAuth()` (`app.ts:862`) ловит отсутствие
identity-ключа, регистрирует устройство и запускает `deviceAuth.startNewDeviceFlow()`.
`registerThisDevice()` (`app.ts:851`) держит регистрацию постоянно.

Но обе запускаются так:

```ts
this.#crypto.init().then(() => {
  setTimeout(() => {
    this.registerThisDevice();
    this.checkDeviceAuth();
  }, this.SETTLE_AFTER_PAINT_MS);   // 2500 мс
});
```

То есть **после первой отрисовки и через 2.5 секунды**. Интерфейс открывается раньше, чем
устройство что-либо сообщает. Это и есть расхождение с требованием 2.

### 1.3 Ключи

Понятия «авторизован» не существует. `device_auth_requests` — это разовые записи
pending/approved/denied, которые переносят **identity-ключ**; решение об авторизации в них
не остаётся и нигде не проверяется.

Раздача группового ключа (`chat.ts:2424`):

```ts
const devices = await this.api.getUserDeviceKeys(userId);
for (const d of devices) { ...wrap and upload... }
```

и `getUserDeviceKeys` (`devices.go:81`) — это `SELECT ... FROM user_devices WHERE user_id = ?`.
**Все** устройства, без разбора авторизации. То есть регистрация в браузере, где есть пароль
от аккаунта, уже даёт доступ ко всем групповым ключам, без одобрения. Требование 3 сейчас
выполняется **наоборот**.

И раздача событийная только частично: её запускает держатель — создание ключа, ротация
эпохи или открытие чата. Устройство, которое только что авторизовали, ждёт, пока кто-то
случайно откроет нужный чат.

Личные чаты — отдельный путь, `message_envelopes` + `getUserDeviceKeys`; требование 3
про них тоже, а не только про группы.

`group_device_key_shares` — фантомная таблица: создаётся миграцией, из неё удаляют при
отзыве устройства (`devices.go:127`), **записи не пишет никто**. Реальные шары живут в
`group_epoch_key_shares` с ключом `(group_chat_id, user_id, device_id, epoch)`.

## 2. Решение, которое снимает большую часть

### 2.1 Ключ группы — на пользователя, не на устройство

Сейчас сырой ключ оборачивается **под ключ каждого устройства**. Отсюда и необходимость
чьей-то активности: обернуть может только тот, у кого сырой ключ есть.

Если оборачивать **под identity-ключ пользователя** — один раз на пользователя на эпоху —
то любое авторизованное его устройство расшифрует шары само. Требование 3 превращается
из «кто-то должен раздать» в «устройство забрало само».

Схема:

```
было:  UNIQUE(group_chat_id, device_id, epoch)   — под device_id
стало: UNIQUE(group_chat_id, user_id, epoch)     — под identity пользователя
```

Изменения: миграция `group_epoch_key_shares` (старые device-шары остаются читаться),
`GetMyGroupDeviceKeyShare` больше не спрашивает `device_id`, раздача оборачивает один раз.

**Размен, который надо решить владельцу.** С per-user шарами новое устройство расшифрует
и **прошлые** сообщения — все эпохи, к которым у пользователя есть доступ. С per-device
оно начинает с нуля. Это разница между «новый телефон видит историю» и «начинает пусто»,
и она касается приватности, поэтому выбирать молча нельзя. Рекомендация — per-user:
семейный сценарий, где телефон и ноутбук должны видеть одно и то же, иначе «новое
устройство» будет вечно отстающим.

### 2.2 Авторизация становится состоянием, а не разовым событием

Добавить в `user_devices`:

| Поле | Значение |
|---|---|
| `authorized` | 0 — зарегистрировано, ключей не получает; 1 — авторизовано, получает |
| `authorized_at` | когда |

Переход в 1 происходит **только** при одобрении в `device_auth_requests` — то есть ровно
тот момент, когда устройство получает identity-ключ. Согласованность обеспечивается тем,
что и identity-ключ, и флаг ставятся в одном обработчике.

`getUserDeviceKeys` начинает отдавать **только** `authorized = 1`. Это чинит и требование 3
(получают авторизованные), и убирает дыру, где любой вход с паролем давал все ключи.

### 2.3 Одно устройство — один `deviceId`, и он не перерождается молча

- Закрыть дыру в `ensureDeviceKeyPair`: нет `deviceId` при живых ключах — значит сгенерировать
  его там же, где он и живёт.
- Сделать уникальность **в паре с пользователем**: `UNIQUE(user_id, device_id)`, миграцией.
  Это убирает поломку с общим браузером: устройство второго участника станет своей строкой
  и получит свои ключи.
- `logout` на этом браузере должен предлагать «выйти и стереть ключи с устройства» —
  иначе следующий вошедший унаследует чужие ключи. По умолчанию стирать, с явным
  подтверждением, потому что обратное — «устройство доверенное» — тоже осознанный выбор.
- Дубли в списке: если `device_public_key` совпал у двух строк, это одно устройство —
  схлопывать при отображении и чистить лишнюю строку.

## 3. Порядок работ

Каждый шаг полезен сам по себе, следующий не обязан ждать предыдущего.

**Шаг 1. Убрать дыру в `deviceId` и починить список устройств.** Наименьшее изменение,
снимает половину пункта 1: генерация при недостающих ключах, схлопывание по
`device_public_key`, понятная метка «это устройство» в интерфейсе.

**Шаг 2. Флаг `authorized`.** Колонка, запись в обработчике одобрения, фильтр в
`getUserDeviceKeys`. С этого момента «получить ключи» перестаёт означать «уметь зайти
с паролем» — и требование 3 начинает значить то, что вы имеете в виду.

**Шаг 3. Раздача по событию авторизации.** После перехода в `authorized=1` разослать
участникам событие `device_authorized`, и держатели, у которых в памяти есть ключи
групп, раздают их этому устройству. Это промежуточный вариант: работает до сих пор без
миграции схемы, закрывает «не ждать, пока кто-то откроет чат».

**Шаг 4. Per-user шары вместо per-device.** Схема, миграция, раздача в один заход. После
этого шаги 3 по сути больше не нужны, и раздача становится обычной выборкой.

**Шаг 5. Гейт до интерфейса.** Требование 2. Отдельная работа, потому что это правка
последовательности загрузки, а её легко сломать, делать раньше остального.

## 4. Гейт на новом устройстве (требование 2)

Сейчас определение нового устройства происходит через 2.5 с после первой отрисовки.
Нужно наоборот: показывать экран подключения **до** отрисовки интерфейса.

Предлагаемая последовательность:

```
старт приложения
  ├─ localStorage: нет currentUser → экран входа как сейчас
  └─ currentUser есть
       ├─ IndexedDB: identity-ключ есть
       │    → обычный запуск; позади (после отрисовки) регистрация устройства,
       │      как сейчас — она на отображение не влияет
       └─ identity-ключа нет
            ├─ оставить экран входа на месте, поверх — полноэкранный шаг:
            │  «Подключение устройства»
            │    1. проверяем пароль от аккаунта (он уже есть в сессии)
            │    2. `ensureDeviceKeyPair()` + `POST /devices/register` → authorized = 0
            │    3. `device_auth_requests` → ожидание одобрения существующего устройства
            │    4. одобрено → принять identity-ключ, authorized = 1
            │    5. забрать ключи всех чатов (шаг 4) и только потом открыть интерфейс
            └─ отказ или таймаут → объяснить, что без ключа история не читается,
               и не пускать в пустой интерфейс
```

Два решения, которые нужно принять осознанно:

- **Разблокировать интерфейс без ключа или нет.** Требование говорит «до открытия
  интерфейса», то есть блокировать. Но если у человека нет второго устройства, чтобы
  одобрить, он запрогнется намертво. Нужен выход: объяснить и дать войти **без
  расшифровки** — читать ленту и писать, но история чатов останется непрочитанной.
  Это честнее, чем пустой интерфейс с ошибками расшифровки.
- **Что показывать во время ожидания одобрения.** Экран должен объяснять, что происходит
  и что делать: «откройте MeowChat на устройстве, где уже есть ключ, и подтвердите
  вход». Плюс возможность отозвать запрос, если он больше не нужен.

## 5. Решения владельца (приняты 2026-10-11)

1. **История — новое устройство видит.** Значит §2.1 делается в варианте **per-user**:
   шары оборачиваются под identity-ключ пользователя, новое устройство подхватывает все
   эпохи само.
2. **Интерфейс не блокируется.** Экран подключения — визуальный слой поверх, backdrop
   диалога; навигация и маршруты продолжают работать.
3. **Авторизованное устройство остаётся авторизованным после выхода из аккаунта** и
   получает ключи при повторном входе по ранее авторизованному `deviceId`.

### 5.1 Оговорка к решению 2

«Не блокировать» не значит «делать вид, что ничего не происходит». Пока ключ не пришёл,
чат всё равно попытается расшифровать тред и покажет `[Зашифрованное сообщение]` — то есть
тот самый вид ошибки, который и вызывает вопросы. Поэтому условие неблокирующего экрана:
до получения ключей расшифровка **не запускается**, а вместо неё показывается «ожидаем
ключ» с объяснением. Это правка состояния, а не блокировки.

### 5.2 Что нужно, чтобы решение 3 было выполнимо

Здесь поправка к формулировке «получит ключи по ранее авторизованному `deviceId`».
**Чистить ключевой материал целиком нельзя**, иначе решение не работает:

```
устройство зарегистрировано и авторизовано
  device_public_key = SPKI_old           <- в строке user_devices

выход из аккаунта, чистим хранилище
  -> ensureDeviceKeyPair() генерирует НОВУЮ пару
  -> device_public_key = SPKI_new != SPKI_old

повторный вход, сервер видит тот же deviceId, authorized = 1
  -> но обернуть ключ для SPKI_new он не может: в строке SPKI_old
  -> и доказать, что это то же устройство, нечем
```

Авторизация по `deviceId` работает только при **сохранении пары устройства**. Значит
разделение такое:

| Что | Область | При выходе |
|---|---|---|
| `deviceId`, `deviceKeyJWK`, `devicePublicKeySPKI` | **устройство** | **сохранять** |
| `identityKeyJWK`, `publicKeySPKI` | **человек** | **чистить** |

Это не компромисс, а прямое требование: устройство опознаётся по своей паре, человек — по
своему identity-ключу, и путать их нельзя.

### 5.3 И тогда «чистить» окупается: identity-ключ возвращается без второго устройства

Чистка была опасна только тем, что identity-ключ после неё некуда деть. Но
`POST /devices/recover` с `{method: "password", input: <пароль от аккаунта>}`
(`devices.go:307`) уже умеет вернуть его по паролю, а не по устройству. Получается
замкнутый вход без тупика:

```
вход -> deviceId известен и authorized = 1
     -> спросить пароль от аккаунта
     -> POST /devices/recover      -> identity-ключ обратно в браузер
     -> per-user шары всех чатов   -> история на месте (решение 1)
     -> готово, второе устройство не нужно
```

Это снимает тупик, из-за которого в §4 предлагалось «пускать без ключа»: раньше
единственным источником identity-ключа был другой девайс, теперь — пароль, который у
человека и так есть.

### 5.4 Цена решения 3: `deviceId` становится credential

Сейчас `deviceId` — просто идентификатор, и сервер не проверяет, что вызывающий владеет
парным приватным ключом. Если по нему выдают ключи, он становится **bearer-токеном**, и
это надо закрыть:

- **Хранить на сервере только хэш.** Сырое значение серверу не нужно — достаточно
  сравнения хэшей, как у пароля.
- **Убрать из access-логов.** `deviceId` ходит query-параметром (`api.service.ts:1272`),
  а `log_format timed` (`nginx.conf:48`) пишет `$request` целиком. Логи на этом сервере уже
  выдавали живые JWT — тот же класс проблемы.
- **Не отдавать чужие `deviceId`.** `GET /users/:id/device-keys` возвращает `device_id`
  партнёрам по чату. Здесь помощь неожиданная: с переходом на **per-user шары** (§2.1)
  чужие `device_id` больше не нужны вообще — `distributeGroupKeyToMemberDevices` оборачивает
  ключ под **identity** пользователя, то есть передавать достаточно публичный ключ.

Значит §2.1 не только решает задачу 3, но и **закрывает утечку, которую создаёт решение 3**.
Порядок работ из §3 становится не просто удобным, а вынужденным.

### 5.5 Порядок шагов с учётом решений

| Шаг | Что | Препятствие для следующего |
|---|---|---|
| 1 | Дыра `deviceId`, схлопывание дублей, `UNIQUE(user_id, device_id)` | нет |
| 2 | Per-user шары вместо per-device (§2.1) | миграция данных |
| 3 | Флаг `authorized` + фильтр в `getUserDeviceKeys` | нет |
| 4 | `deviceId` как credential: хэш в БД, чистка логов | нет |
| 5 | Повторный вход: recognize -> пароль -> `/devices/recover` -> шары | требует 2 и 4 |
| 6 | Экран подключения без блокировки (§5.1) | требует 3 |

Шаг 5 — тот самый «вход по `deviceId`», и он последний не случайно: держится на per-user
шарах и на хэшировании.

## 6. Что поправить в `e2ee-new-device-key-flow.md`

Раздел 6 старого плана говорит «Регистрация нового устройства — нет». Это уже не так:
`registerThisDevice()` регистрирует при каждом входе, а `checkDeviceAuth()` — при первом.
Устарела и строка про `PutKey`: он по-прежнему перезаписывает identity-ключ аккаунта,
но следствие изменилось — новое устройство получает identity-ключ через
`device_auth_requests`, то есть перезапись больше не главный барьер, а второй по
значимости.

## 7. Чего эта стратегия не решает

- **Отзыв устройства.** По-прежнему слабый: устройство держит identity-ключ и может
  зарегистрироваться заново. Ограничение из `CHANGELOG.md` остаётся в силе.
  Per-user шары его не усиливают, но и не ослабляют.
- **Федерация.** Ключевой материал на federated-пире, стратегия их не рассматривает.

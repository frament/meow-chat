# Ключи при авторизации: как это устроено и почему новый браузер остаётся без ключа

Документ отвечает на вопрос владельца после жалобы 2026-10-10: новый браузер на Windows,
авторизация, группа — весь тред в `[Зашифрованное сообщение]`.

Разбор с прод-данными — в `2026-10-10-group-key-request-and-sticker-pipeline.md`. Здесь
сама схема и предлагаемое решение: **что должно происходить при входе**, чтобы новое
устройство не осталось читателем без ключа.

---

## 1. Три ключа, и их легко спутать

| Ключ | Где живёт | Для чего | Устройство-specific? |
|------|-----------|----------|---------------------|
| **identity** | `user_keys` на сервере + `identityKeyJWK` в IndexedDB | ECDH между **людьми**: личные чаты, legacy-шара ключа группы | Нет — **один на аккаунт** |
| **device** | `user_devices` + `deviceKeyJWK` в IndexedDB | ECDH между **устройствами**: обёртка ключа группы под конкретное устройство | Да |
| **group** | `group_messages.encrypted_content` зашифрован им | Симметричный AES-256-GCM, общий для всех участников | Нет — **один на группу** (и на эпоху) |

Смешение identity и device — главный источник путаницы в этом коде: имена похожие,
назначение разное, а ECDH у них одинаковый, поэтому ошибка не бросается в глаза.

## 2. Как происходит отправка (рабочий путь)

```
Участник А                          Сервер                        Участник Б
    │                                  │                              │
    │ getGroupKey(группа, эпоха)        │                              │
    │  ├ кэш                            │                              │
    │  ├ IndexedDB (этот браузер)       │                              │
    │  ├ device-шара: GET /my-device-key│                              │
    │  └ legacy: GET /my-key + ECDH    │                              │
    │            с identity каждого     │                              │
    │─────────────────────────────────►│                              │
    │◄─────────────────────────────────│                              │
    │ AES-GCM(content, groupKey)        │                              │
    │                                  │                              │
    │ POST /group-chat-messages        │                              │
    │   encrypted_content              │                              │
    │─────────────────────────────────►│ INSERT group_messages        │
    │                                  │─────────────────────────────►│ WS: encrypted_content
    │                                  │                              │
    │◄── GET /group-chats/:id/members ─│ (при запросе ключа)          │
    │    getUserDeviceKeys(member)      │                              │
    │    для каждого: ECDH(myIdentity,  │                              │
    │                  devicePublic)     │                              │
    │    → AES-wrap(groupKey)          │                              │
    │─────────────────────────────────►│ INSERT group_epoch_key_shares │
```

Ключ раздаётся **тем, кто попросил**, и **держатели шарят сами**. Раздачи по кнопке нет:
`selectGroup` вызывает `distributeGroupKeyToMembers` при каждом открытии чата.

## 3. Где ломается вход на новом устройстве

```
Новый браузер, устройство D, вход пользователя U
    │
    ├─ ensureIdentityKey(): в IndexedDB пусто
    │    → генерируется НОВАЯ identity-пара (identity_new)
    │    → PUT /keys  →  server_keys[U] := identity_new   ← перезапись!
    │
    │  ┌──────────────────────────────────────────────────────────┐
    │  │ Что теперь не сходится:                                   │
    │  │                                                          │
    │  │  legacy-шара группы зашифрована ECDH(identity_old, X)    │
    │  │  ключ нового браузера — identity_new, а не identity_old    │
    │  │  ⇒ расшифровать нечем, ни с одним участником             │
    │  │                                                          │
    │  │  device-шара приходит под devicePublic(D) + identity       │
    │  │  отправителя, но сам ключ D ещё не создан                 │
    │  │  ⇒ ensureDeviceKeyPair() создаёт его ПОЗЖЕ, а раздача      │
    │  │    идёт только по списку user_devices, где D нет          │
    │  └──────────────────────────────────────────────────────────┘
    │
    ├─ crypto.init() завершается
    │
    └─ selectGroup(группа)
         ├ getGroupKey() → IndexedDB пусто, device-шара нет,
         │                  legacy не расшифровывается → null
         └ (до 2026-10-10: тишина)
              (после: requestGroupKeyForRead → WS group_key_request)
```

Серверный след на проде подтверждает каждый шаг: у зашедшего пользователя
`user_devices` пуст, в `group_epoch_key_shares` для группы 2 нет ни строки с его
устройством, а `decrypt_failures` содержит пять записей `no_group_key` за минуту.

**Ключевое отличие от «просто гонки»:** даже если попросить ключ сейчас, его не пришлют
некому — держатели шарят под **devicePublic**, а устройства D в `user_devices` нет.
Запрос сам по себе проблему не закрывает, он нужен вместе с регистрацией устройства.

## 4. Что не так по сути

`PutKey` перезаписывает ключ аккаунта. Для одного устройства это безобидно: оно владеет
и старым, и новым ключом. Для **второго** браузера — разрушительно: он аннулирует
пару первого, и всё, что первое устройство обёрнуло для этого пользователя, становится
нечитаемым.

Формально это тот же класс, что описан в `docs/plans/per-device-e2ee.md` §12
(отозванное устройство может перерегистрироваться), только без отзыва.

Есть ещё следствие, менее очевидное: **перезапись ломает и другие устройства.** Если
у пользователя есть телефон со старым identity-ключом, а он заходит с нового браузера —
`user_keys[U]` становится `identity_new`, и телефон, отправляющий сообщения, будет
пользоваться чужим для ECDH ключом. Проверить это стоит отдельно, но по коду путь
записи общий.

---

## 5. Предлагаемая схема

### 5.1 Не перезаписывать, а заводить устройство явно

**Шаг 1. Устройство регистрируется само, при первом `cryptoReady()`.**
Сейчас `ensureDeviceKeyPair` ленивый, а `user_devices` пополняется только из UI
(`/devices/register`). Новое устройство отсюда не вытекает — а значит, не получает
и шары. Регистрация при инициализации закрывает это: устройство появляется в списке,
и следующая раздача (а `selectGroup` раздаёт при каждом открытии) до него дойдёт.

**Шаг 2. `PutKey` перестаёт перезаписывать ключ, которым владеет кто-то ещё.**

Здесь нужна развилка, и она продуктовая:

- **(а) Один identity-ключ на аккаунт, привязанный к первому устройству.** Новый браузер
  обязан восстановить его из резервной копии. Плюс: ничего не ломается ни у кого.
  Минус: без копии — доступ к старым сообщениям потерян, нужен понятный сценарий отказа.
- **(б) Ключ на устройство, legacy-путь выпиливается.** `user_keys` становится
  `UNIQUE(user_id, device_id)`, все шары — только device-уровня. Плюс: каждое
  устройство самостоятельно, перезаписи нет by construction, отзыв устройства честный.
  Минус: миграция данных и обратной совместимости с уже разосланными legacy-шарами;
  для `epoch > 0` device-путь уже единственный, так что это продолжение существующего
  курса, а не новая идея.

**Рекомендация — (б)**, с оговоркой: путь `epoch > 0` в `getGroupKey` уже возвращает `null`
без device-шары, то есть система наполовину живёт по (б) и наполовину по (а), и
это состояние хуже любого из двух. Но выбор за владельцем: (а) дешевле, (б) честнее.

**Шаг 3. Восстановление при входе с нового устройства — обязательный путь, а не опция.**
`importIdentityKey` в сервисе есть и работает, но не вызывается из UI ни разу. Нужен
экран: «на этом устройстве нет ключа аккаунта — восстановить из резервной копии?», с
вводом пароля от аккаунта. `uploadKeyBackup`/`recoverKeys` в настройках уже есть,
и пароль аккаунта там используется как секрет.

### 5.2 Раздача ключей должна быть событийной, а не «при открытии чата»

Сейчас: держатель шарят при каждом `selectGroup`. Отсюда следует, что новое устройство
получит ключ **только когда держатель сам откроет этот чат**, а он может не открывать
неделями.

Нужно: при регистрации устройства (шаг 1) держатели группы узнают об этом и раздают
ключ. Тогда появление нового устройства — событие, а не совпадение.

### 5.3 Что должно происходить при входе — итог

```
Вход
 ├─ identity: есть в IndexedDB? → ок
 │            нет → спросить: восстановить из копии или создать новый
 │                  (с явным предупреждением при «новый»: старые личные
 │                   сообщения останутся непрочитанными)
 ├─ device: зарегистрировать, если нет
 └─ при входе в группу:
      ├ ключ есть → расшифровать, раздать (как сейчас)
      └ ключа нет → запросить ключ у держателей (уже сделано 2026-10-10)
                    и показать «ожидаем ключ», а не заглушку
```

Последний пункт — про честность интерфейса: вместо `[Зашифрованное сообщение]`, которое
выглядит как ошибка расшифровки, должно быть «ожидаем ключ чата» с объяснением, что
происходит, и что делать, если ключ не придёт.

| Перезапись identity-ключа | нет — Backlog, нужно продуктовое решение |
| Восстановление ключа при входе | нет — Backlog |
| Событийная раздача ключей | нет — Backlog |
| Понятное «ожидаем ключ» вместо заглушки | нет — Backlog |

Первый слой — необходимое условие, но без второго и третьего он не решает проблему:
просить некого.

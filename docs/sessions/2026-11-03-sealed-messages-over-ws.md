# Запечатанные сообщения приходили пустыми пузырями

Дата: 2026-11-03
Ветка: `main`.
Задача владельца: «давай с сообщений, только перед тем как что-то исправлять перепроверь,
что уже не решена проблема».

## 1. Перепроверка: проблема не решена, и вот чем это доказано

Проверял не по памяти из прошлой сессии, а по трём независимым источникам.

| что смотрел | результат |
|---|---|
| `PINNED_SERVER_KEY_FINGERPRINT` | **пуст** — слой выключен в собранном клиенте |
| кадр WebSocket (`runHub`, `handlers.go`) | поля `server_envelope` **нет** |
| WS-обработчик клиента (`chat.ts`) | `server_envelope` **не упоминается** ни разу |
| прод-база | 4 строки `crypto_scheme='server'`, у всех `content` пуст |

Строки с прода — 25.10, 17:59–18:02, между пользователями 1 и 2, то есть как раз окно,
когда pin был включён:

```
id 286  sender 1 → 2  content_len 0  enc_len 44  17:59:12
id 287  sender 2 → 1  content_len 0  enc_len 44  17:59:54
id 288  sender 2 → 1  content_len 0  enc_len 44  18:01:30
id 289  sender 1 → 2  content_len 0  enc_len 48  18:02:03
```

И тест, который это ловит, до правки был красным — оба теста (с ключом и без):

```
--- FAIL: TestWebSocket_ServerSchemeMessageArrivesReadable
    the frame carries no envelope: a live thread shows an empty bubble and only a
    reload produces text
--- FAIL: TestWebSocket_ServerSchemeWithoutKeySaysSo
    needs_key = <nil>, want true
```

**Причина.** В строке лежит только шифртекст покоя, `content` пуст. Прочитать текст
клиент может единственным способом — получить конверт, обёрнутый на его ключ. Путь
чтения (`GET /api/messages` → `openServerScheme`) это делает. Кадр сокета — нет: он
собирается отдельно, в `runHub`, и про новую схему не знал. Отсюда ровно то, что
видел получатель: живой пузырь пустой, после перезагрузки текст на месте.

Класс дефекта знаком: `sticker_url` уже пропадал так же 09.10. Второй раз — потому что
полей в кадре два набора, событийный и читаемый, и они копируются руками.

## 2. Что сделано

**Сервер.** Текст, открытый из конверта при сохранении, теперь доезжает до хаба
(`wsMessage.serverPlaintext`) и там запечатывается **для каждого соединения
отдельно**: получателю — на его ключ, остальным устройствам отправителя — на их.
Функция `sealForReader` в `crypto_read.go`, рядом с `activeReceiveKey`, которую
использует и путь чтения: одна реализация «чей ключ», а не две.

Два честных исхода, третьего нет:

- конверт есть — клиент показывает текст;
- ключа на аккаунте нет — `needs_key: true`, и клиент пишет «Ключ на этом устройстве не
  настроен». Пустой пузырь читается как удалённая история, поэтому его нет ни в одном
  исходе.

Заодно кадр больше не несёт `encrypted_content` для схемы `server`: это шифртекст
покоя, клиент его открыть не может, а выглядел он как обычное E2EE-сообщение с пустым
iv. Путь чтения так не делал с самого начала — расхождение было только в кадре.

**Клиент.** В WS-обработчике появилась ветка для конверта: дождаться ключа аккаунта,
открыть, при неудаче — `needs_key`. Плюс защита от гонки: `ensureAccountKey` теперь
держит **обещание в полёте**. Раньше одновременные вызовы (старт приложения и первое
входящее сообщение) генерировали **два** ключа: первый регистрировался, второй получал
409 и всё равно записывался на устройство — аккаунт оставался с ключом, приватной
половины которого нет ни на одном устройстве.

## 3. Проверка

| тест | что доказывает |
|---|---|
| `TestWebSocket_ServerSchemeMessageArrivesReadable` | полный путь POST → хаб → сокет; конверт из кадра открывается **приватным ключом получателя** в исходный текст, `kid` — его |
| `TestWebSocket_ServerSchemeWithoutKeySaysSo` | без ключа `needs_key`, конверта нет, шифртекст покоя не отправлен |
| `chat.server-scheme.spec.ts` (3 спека) | настоящая подписка компонента: текст появляется в треде; неоткрывающийся конверт даёт `needs_key`; `needs_key` от сервера доезжает |

Тест ходит через настоящий `POST /messages`, а не подкладывает сообщение прямо в
`h.broadcast`: половина, где текст теряется, — именно эта.

**Мутации, все краснеют:**

- убрать запечатывание в хабе → оба Go-теста;
- `needs_key = false` вместо `true` без ключа → тест без ключа;
- клиент снова не читает конверт → спеки 1 и 2;
- `else needsKey = false` при неудачном вскрытии → спека 2;
- `needs_key: false` в сообщении → спеки 2 и 3.

Go целиком зелёный, фронтенд 529 (было 526).

## 4. Чего это не доказывает

**Живой проверки на устройстве нет.** Pin выключен, значит на проде этот код сейчас не
исполняется: сборка безопасна, но и не показывает ничего. Порядок, записанный в
`ROADMAP.md`, остаётся: локальный инстанс с pin, два пользователя, одно сообщение,
консоль на виду — и только потом pin обратно и номер 1.8.0.

**Четыре старых сообщения (286–289) я не проверял на чтение**: они идут путём
`GET /api/messages`, который не менялся и покрыт тестами; их `content` пуст по
устройству схемы, а не по ошибке.

**Гонку двух конвертов не воспроизводил под нагрузкой** — она закрыта формой кода
(обещание в полёте), а не тестом. Если понадобится доказательство, это отдельный спек
на два одновременных `ensureAccountKey`.

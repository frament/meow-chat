# Сессия 2026-09-28…10-01: пуш-тег, телеметрия расшифровки и мультидевайс E2EE

## Контекст

Началось с разбора трёх сообщений Екатерина → frament: первое «не пришло», третье «пришло с опозданием». По ходу выросли в отдельную большую тему — полноценный мультидевайс E2EE (телефон + ПК), который до этого не работал вообще.

Прод: home-lab `192.168.1.41`, проект `~/rep/my-chat`, Docker Compose.

## 1. Разбор пушей (2026-09-28)

По `push_logs` и логам backend для 3 сообщений (id 247/248/249): все три сервер отправил на FCM + Apple со `201`, ошибок нет. Клиентские `received/shown`:
- 247 — **нет вообще** (service worker не вызывался),
- 248 — через 8 с,
- 249 — через 40 с.

Причина «потерянного» первого: у всех сообщений от одного отправителя был **общий `tag`** (`chat-<senderId>`), а `requireInteraction: true` и `renotify` отсутствовали. Пока телефон спал, iOS/APNs свернул очередь по тегу и отдал только последнее. Задержка третьего — обычная фоновая доставка APNs.

**Фикс:** `push.go:pushTag` добавляет к тегу уникальный `ackId` на каждую доставку; из SW убран `requireInteraction` (iOS не поддерживает, Android делает «липким»).

## 2. Групповой ключ новым участникам (2026-09-28)

Новый участник не мог отправить первое сообщение: шэр группового ключа создавался только когда владелец ключа **откроет** группу, а отправка без ключа блокировалась («Не удалось зашифровать: нет ключа группового чата»).

**Фикс:** `POST /group-chats/:id/request-key` + broadcast `group_key_request`; при добавлении участника (по имени и по инвайту) — broadcast `group_member_added`; после `UploadGroupKeyShare` получателю летит `group_key_ready`. Клиент при отсутствии ключа запрашивает его и **авто-ретраит** отправку, когда ключ приходит.

## 3. Телеметрия расшифровки (2026-09-29)

Перед мультидевайс-миграцией нужно было понять, теряют ли пользователи сообщения. Добавлено:
- таблица `decrypt_failures` + `POST /api/e2ee/decrypt-failed` (auth, retention 30 дней);
- клиент раз в сессию на диалог шлёт причину (`no_peer_key` / `no_group_key` / `decrypt_failed`);
- админ-вкладка **«Расшифровка»** со сводкой и списком.

Baseline за 2 дня на проде: **1 ошибка** (frament, ЛС с Екатериной), совпала по времени с перезагрузкой identity-ключа — это был кейс мультидевайса, не массовая потеря. Групповых ошибок 0.

## 4. Мультидевайс E2EE (Фазы 0–4 + финальный шаг)

### Что было не так

Linking устройств **никогда не работал** — нашли и починили четыре баги:
1. WS `device_auth_request` не содержал `device_public_key` → доверенное устройство не могло зашить ключ;
2. `CreateAuthRequest` возвращал 409 (приложение регистрирует устройство до запроса);
3. `decryptIdentityKeyFromDevice` вызывался с ключом самого нового устройства, а не доверенного;
4. `ensureDeviceKeyPair` генерировал non-extractable ключ и потом экспортировал его JWK → падало; identity JWK хранился то объектом, то строкой.

Дополнительно: `user_keys` — одна строка на пользователя, а `group_key_shares` — user-level; второе устройство данные расшифровать не могло.

### Фаза 0 — рабочий linking
WS-событие теперь несёт публичный ключ устройства; `CreateAuthRequest` идемпотентен; на approve сохраняется `approver_public_key`; фикс `ensureDeviceKeyPair` и хранения JWK. В настройках — раздел **«Устройства»**: список, отключение, «Подключить это устройство к аккаунту» (`DeviceLinkService` → диалог подтверждения).

### Фаза 1 — реестр device-ключей
`GET /users/:id/device-keys`; каждое устройство регистрирует свой ключ при старте.

### Фаза 2 — DM-конверты
`message_envelopes` + `messages.env_content/env_iv`: текст шифруется случайным контент-ключом, ключ оборачивается на каждое устройство получателя и свои устройства. Новый клиент предпочитает конверт, иначе — legacy-путь.

### Фаза 3 — групповые ключи на устройство
`group_device_key_shares` (device + epoch); раздача ключа на все устройства участников; `getGroupKey` берёт device-шэр.

### Фаза 4 — recovery/backup
`GET /devices/backup-status` + раздел настроек **«Резервная копия ключа»**: копия по паролю и фраза восстановления (PBKDF2-SHA256 + AES-256-GCM, совместимо с серверным recovery).

### Финальный шаг — per-device отправитель + эпохи/ротация
- DM-конверты привязаны к **device-ключу отправителя** (`messages.sender_device_id`): `ECDH(senderDevicePriv, recipientDevicePub)` ↔ `ECDH(devicePriv, senderDevicePub)`; account-ключ оставлен фолбэком.
- `group_messages.epoch` + `group_epoch_key_shares(group, device, epoch)` + `GET /group-chats/:id/key-epoch`; клиент хранит ключи по эпохам и дешифрует сообщение его эпохой → история не ломается.
- `DELETE /devices/:id` удаляет шэры устройства и рассылает `device_revoked`; остальные устройства аккаунта генерируют эпоху `+1` и раскладывают её на все оставшиеся устройства → отозванное устройство не читает новые групповые сообщения.

### Инвариант single-device

Большинство пользователей — одно устройство. Все шаги **аддитивны**: legacy user-level шэры и account-ключевой путь сохранены, при неудаче — фолбэк. Linked/single-device пользователи не затронуты. Do-not-break список — в `docs/plans/per-device-e2ee.md` (§11).

## Ограничения и TBD

- **Отзыв устройства** криптографически работает для новых сообщений (эпоха/конверты), но отозванное устройство всё ещё имеет учётные данные аккаунта и может зарегистрироваться заново. Жёсткая защита — вне E2EE (нужна per-device-аутентификация).
- Кросс-девайс проверку вживую (телефон+ПК) **не гоняли** — по решению пользователя пропустили. Рекомендуется прогнать сценарий linking + отзыв перед «боевым» использованием.
- Leader legacy `user_keys`-путь и user-level шэры сознательно сохранены (инвариант single-device), удаление — отдельным решением.
- Полная серверная пагинация истории (>100) всё ещё не сделана.

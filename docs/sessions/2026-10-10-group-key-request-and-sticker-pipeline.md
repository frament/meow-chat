## 2. №1 Почему ключ не приходил — три слоя

### Слой 1: запроса не было вовсе

`requestGroupKey` вызывался ровно в одном месте — когда **отправка** не смогла зашифровать
(`chat.ts:1970`). Читающий пользователь ключ не просил никогда. Открыл группу → не
расшифровалось → `[Зашифрованное сообщение]` → и тишина.

**Правка:** `requestGroupKeyForRead()` в `selectGroup`, когда `getGroupKey` вернул `null`.
Один раз на группу за сессию (`keyRequestedForRead`) — запрос уходит всем участникам через
WS, и каждый заново оборачивает ключ; флаг сбрасывается в `onGroupKeyReady`, чтобы
последующая потеря ключа снова была вылечима.

### Слой 2: новый браузер получает новый identity-ключ

Вот это неочевидно и стоит записать отдельно. `ensureIdentityKey` (`crypto.service.ts:64`)
находит в IndexedDB только `identityKeyJWK`; в новом браузере его нет, поэтому генерируется
**новая пара**, и `PutKey` (`e2ee.go:23`) делает:

```sql
INSERT INTO user_keys (user_id, public_key) VALUES (?, ?)
 ON CONFLICT(user_id) DO UPDATE SET public_key = excluded.public_key
```

То есть новый браузер **перезаписывает** публичный ключ аккаунта. Дальше:

- legacy-шара (`group_key_shares`) зашифрована под **старый** identity-ключ этого же
  пользователя → ECDH не сходится → `decrypt` возвращает `null` → `continue` по всем
  участникам;
- device-шары приходят под device-ключ и identity-ключ отправителя, но самого device-ключа у
  нового устройства раньше не существовало → `tryGetDeviceGroupKey` уходил в `return null`.

`importIdentityKey` в сервисе есть и работает, но **не вызывается ни из одного места UI**.

### Слой 3: почему это не чинится само

`docs/plans/per-device-e2ee.md` §12 описывает остаточное ограничение: отозванное устройство
может перерегистрироваться. Тот же механизм, только без отзыва: новый браузер создаёт новое
устройство, а пути «принести старый ключ» у пользователя нет — резервная копия ключа есть в
настройках, но восстановления при входе с нового устройства тоже нет.

**Что исправлено сейчас:** слой 1. Слои 2 и 3 — это отдельная работа (см. Backlog), она
затрагивает восстановление ключей при входе и требует продуктового решения: «восстановить из
резервной копии» против «пересоздать ключ и потерять доступ к старым сообщениям».

## 3. №2 Стикеры не отправлялись вообще

Проверка базы, а не интерфейса:

```
group 2: msg_type='image' → 5 шт., 'text' → 24 шт., 'sticker' → 0
последнее сообщение в группе 2: id=45, 2026-10-09 16:22
```

Стикеров в группе нет **вообще**, и последнее сообщение старше текущего времени. То есть
Екатерина не отправила их на этот сервер — сообщения не доходили. В логах nginx за 6 часов
нет ни одного `POST /api/group-chat-messages`.

Значит проблема на **отправляющей стороне**: либо стикер не отправляется, либо отправка
уходит с ошибкой, которую интерфейс не показывает. Это требует проверки на устройстве
Екатерины — на сервере следов нет, и выдумывать причину я не стал. Заведено в Backlog с
описанием того, что именно нужно проверить.

Стоит отметить: вчерашняя правка `sticker_url` (#35) тут ни при чём — она про **отображение**
у отправителя, когда отправка уже произошла.

## 4. №3 Стикеры действительно не сжимались

Проверено на прод-файле:

```
-rw-r--r-- 1 root root 3135669 окт 9 21:28 sticker_4_0.png     ← 3.1 МБ
```

Причина: `AdminUploadSticker` вызывал `c.SaveFile` напрямую, минуя `imageproc.Store` — в
отличие от всех остальных путей загрузки. Точное место расхождения уже было описано в
`AGENTS.md` («Stickers are deliberately left alone») — то есть исключение было
сознательным, но стоило 3 МБ на стикер.

**Правка:** загрузка через `saveImage`. Что это даёт и что требует осторожности:

- сжатие (проверено тестом: 190 179 → 72 629 байт на JPEG 1200×1200);
- **расширение из байтов, а не из имени** — JPEG, присланный как `photo.png`, больше не
  сохраняется как PNG (тот же класс, что был описан для фото);
-allowlist расширений на клиентском имени **удалён**: `Sniff` и так проверяет сигнатуру, а
  `.apng` отдельно больше не нужен.

Про **анимацию** — единственное, ради чего исключение существовало: APNG проходит через
`Sniff` как PNG (сигнатура совпадает) и **не пережимается**, то есть остаётся анимированным.
GIF — по той же причине. Перекодирование в JPEG их бы убило.

## 5. №4 Превью изображения не успевало

Причина найдена в `addPreview`:

```ts
private addPreview(file: File) {
  const reader = new FileReader();
  reader.onload = (e) => this.previews.push(e.target!.result as string);  // асинхронно
  reader.readAsDataURL(file);
}
```

`sendMessage` копирует `previews` **на том же ходу**, а `reader.onload` срабатывает позже.
Выбрал файл → сразу отправил → в оптимистичный бакет попал пустой массив → сообщение ушло без
картинки и осталось пустым до перезагрузки.

**Правка:** `addPreview` возвращает промис с data-URL, оба вызова места (`onFileSelected`,
`onPaste`) его ждут. Это и есть смысл слова «не всегда»: если FileReader успевал, всё работало.

## 7. Что осталось незакрытым

Заведено в `BACKLOG.md`:

- **восстановление identity-ключа при входе с нового устройства** (слои 2 и 3 симптома №1) —
  самое важное, без этого новый браузер остаётся читателем без ключа;
- **стикер не отправляется** (симптом №2) — нужен прогон с устройства Екатерины;
- **`group_device_key_shares` — таблица-призрак**: создаётся при миграции
  (`database.go:454`), удаляется при отзыве устройства (`devices.go:127`) и **больше нигде не
  используется**. Реальные шары лежат в `group_epoch_key_shares` (`e2ee.go:158`, `197`,
  `223`). Заведённый контракт без писателя — хуже отсутствия таблицы.
